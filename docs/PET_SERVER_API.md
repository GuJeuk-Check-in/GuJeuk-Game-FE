# 펫타운 서버 API 명세

펫타운(`apps/pet`)의 세이브를 서버에 백업하고 기기 간에 잇기 위해 **새로 필요한
것만** 적는다. 구현 전에 규약을 못 박아 두기 위한 문서다.

- 상태: 구현 완료 (서버 · 클라이언트)
- 대상: `server/` (Spring Boot), `packages/api`, `apps/pet`
- 참조: [펫타운 명세서](PET_TOWN_SPEC.md) §10 세이브 · §13 2단계 서버, [아키텍처](ARCHITECTURE.md)

## 1. 이 문서가 정하지 않는 것

**인증은 새로 만들지 않는다.** 기존 회원 체계를 그대로 쓴다(§2). 랭킹·친구·점수
검증은 이 문서의 범위가 아니다 — 그건 서버가 점수를 계산해야 하는 별도 설계이고,
지금 붙이면 신뢰 경계가 통째로 달라진다(§7).

## 2. 전제 — 인증은 있는 것을 그대로 쓴다

이미 도는 것이고 펫타운이 손댈 이유가 없다.

| 메서드 | 경로            | 인증 | 설명                                   |
| ------ | --------------- | ---- | -------------------------------------- |
| POST   | `/auth/sign-up` | 없음 | 가입. 닉네임 2~12자, 비밀번호 4자 이상 |
| POST   | `/auth/login`   | 없음 | 로그인                                 |

요청 `{ "nickname": "...", "password": "..." }`, 응답
`{ "token": "...", "memberId": 1, "nickname": "..." }`.
이후 요청은 `Authorization: Bearer <token>` 헤더를 붙인다(`JwtFilter`).

**`memberId` 는 펫타운 때문에 추가한 필드다.** 응답에 하나 늘린 것이고 다른 게임은
읽지 않으므로 그대로 돈다. 필요한 이유는 §10 의 저장 키다 — 세이브를 브라우저에
캐시하는데 그 키에 누구 것인지를 적어야 한다. 닉네임으로 대신하지 않는 것은, 서버가
회원을 정하는 값이 언제나 토큰의 subject 인 memberId 라서다. 두 값을 쓰면 로컬 키와
서버 행이 서로 다른 것을 기준으로 갈린다.

### 로그인이 입장 조건이다

**이 문서의 초안은 반대로 적혀 있었다.** "펫타운은 혼자 하는 게임이니 로그인을
뒤로 미루고 로컬 세이브를 정본으로 두자"고 했는데, **운영 환경을 잘못 알고 있었다.**

이 게임은 **기관에서 한 대의 기기를 여러 사람이 번갈아 쓴다.** 로그인하고,
놀고, 로그아웃하고, 다음 사람이 로그인한다. 그 환경에서 "로컬이 정본"은
설계가 아니라 사고다.

- 세이브 칸이 하나면 **다음 사람이 앞사람의 펫을 덮어쓴다**
- 로그아웃해도 로컬에 남아 있으면 **다음 사람이 남의 펫을 본다**
- 마지막에 논 사람의 진행만 남고 나머지는 조용히 사라진다

그래서 뒤집는다. **로그인이 입장 조건이고, 서버가 정본이다.** 로컬 저장은
그 세션 동안의 캐시일 뿐이다. 자세한 규칙은 §10 에 있다.

## 3. 스키마 — `V3__pet.sql`

```sql
CREATE TABLE pet (
    id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    member_id BIGINT NOT NULL,

    -- 나중에 조회 조건이 될 값은 컬럼으로 둔다.
    name VARCHAR(16) NOT NULL,
    level INT NOT NULL DEFAULT 1,
    exp INT NOT NULL DEFAULT 0,
    coins INT NOT NULL DEFAULT 0,

    -- 세이브 스키마 버전(PetSave.version). 서버는 **해석하지 않고 보관만 한다**(§6).
    save_version INT NOT NULL,

    -- 인벤토리·가구 배치·튜토리얼처럼 조회 조건이 되지 않고 모양이 자주 바뀌는 것.
    state_json JSON NOT NULL,

    -- 마지막으로 서버에 반영된 시각. 충돌 판정의 기준이다(§5).
    synced_at DATETIME(3) NOT NULL,

    CONSTRAINT uk_pet_member UNIQUE (member_id),
    CONSTRAINT fk_pet_member FOREIGN KEY (member_id) REFERENCES member (id)
);
```

**컬럼과 JSON 을 섞는 이유.** 전부 JSON 에 넣으면 나중에 "레벨 10 이상 사용자 수"
같은 것을 못 센다. 반대로 전부 컬럼으로 펴면 인벤토리에 물건이 하나 늘 때마다
마이그레이션이 필요하다. **조회할 값만 컬럼으로 꺼낸다.**

**`member_id` 가 UNIQUE 인 이유.** 펫타운은 펫을 한 마리만 키운다(명세 §2).
여러 마리를 허용하면 "어느 펫을 이어받을지" 고르는 화면이 필요해지는데, 그건
이 게임이 하려는 일이 아니다.

**`DATETIME(3)`.** 밀리초까지 둔다. 초 단위면 같은 초에 일어난 두 저장이 같은
시각으로 보여 충돌 판정이 무뎌진다.

## 4. 엔드포인트

전부 `Authorization: Bearer <token>` 이 필요하다. `SecurityConfig` 의
`requestMatchers("/health", "/auth/**", "/ws/**").permitAll()` 목록에 **넣지 않는다.**

### 4.1 `GET /pet` — 서버에 있는 세이브를 가져온다

다른 기기에서 이어받을 때, 그리고 연결 직후 한 번 부른다.

**200 OK**

```json
{
  "save": {
    "version": 1,
    "pet": { "name": "몰랑", "bornAt": 1788000000000, "level": 3, "exp": 40 },
    "stats": { "hunger": 72.5, "mood": 88, "clean": 61, "energy": 94 },
    "wallet": { "coins": 230 },
    "inventory": { "apple": 2, "cushion": 1 },
    "room": { "wallpaper": "default", "floor": "default", "placed": [] },
    "sleep": null,
    "tutorial": { "step": 7, "done": true },
    "daily": { "date": "2026-09-02", "coinsEarned": 120, "checkedIn": true, "pets": 3 },
    "lastSeenAt": 1788262698607
  },
  "syncedAt": 1788262700123
}
```

`save` 는 **클라이언트의 `PetSave` 와 같은 모양 그대로**다(명세 §10). 서버가
따로 가공한 형태를 만들지 않는 이유는, 두 모양이 생기는 순간 어느 쪽이 진짜인지
매번 따져야 하기 때문이다.

**404 Not Found** — 이 계정에 아직 펫이 없다. `{ "message": "저장된 펫이 없습니다." }`

에러가 아니라 정상 상태다. 방금 연결한 사람은 서버에 아무것도 없다.

### 4.2 `PUT /pet` — 세이브를 통째로 올린다

**부분 갱신(PATCH)을 두지 않는다.** 세이브는 한 덩어리이고, 필드 단위로 합치는
것은 명세 §13 이 금지한 자동 병합 그 자체다.

**요청**

```json
{
  "save": { "...PetSave 전체..." },
  "baseSyncedAt": 1788262700123
}
```

`baseSyncedAt` 은 **이 클라이언트가 알고 있는 마지막 서버 시각**이다. 처음
올리는 경우(서버에 펫이 없을 때)에는 `null` 을 보낸다.

**200 OK** — `{ "syncedAt": 1788262800456 }`

클라이언트는 이 값을 다음 `baseSyncedAt` 으로 들고 있는다.

**409 Conflict** — 서버가 더 최신이다. 본문에 **서버 상태를 그대로 실어 준다.**

```json
{
  "message": "다른 기기에 더 최근 진행이 있습니다.",
  "server": { "save": { "..." }, "syncedAt": 1788262900000 }
}
```

한 번 더 받으러 가지 않아도 되게 여기에 담는다. 충돌은 사용자에게 물어야 하는
상황이고, 그 화면을 그리는 데 필요한 값이 이미 서버에 있기 때문이다.

### 4.3 `DELETE /pet` — 서버에 남은 내 펫을 지운다 (2순위)

연결을 끊는 것 자체는 클라이언트가 토큰을 버리면 끝이지만, **서버에 남은 자기
데이터를 지울 방법이 없으면 안 된다.** 첫 구현에서 빠져도 게임은 돌아가므로
2순위로 둔다.

**204 No Content** — 지웠거나, 원래 없었다(멱등).

## 5. 충돌 규약 — 자동으로 합치지 않는다

명세 §13 이 못 박은 규칙이다. **조용한 자동 병합은 진행이 사라지는 사고의
원인이 된다.**

판정은 단순하다.

```
요청의 baseSyncedAt ≠ DB 의 synced_at  →  409
```

- `baseSyncedAt` 이 `null` 인데 DB 에 이미 있으면 → 409
- DB 에 없는데 `baseSyncedAt` 이 있으면 → 그냥 새로 만든다(서버 데이터가 지워진
  경우다. 여기서 막으면 사용자는 영영 올릴 수 없다)

**클라이언트는 409 를 받으면 사용자에게 묻는다.**

> 다른 기기에 더 최근 진행이 있어요. 어느 쪽을 쓸까요?
> [이 기기 것으로 덮기] [다른 기기 것 가져오기]

"이 기기 것으로 덮기"를 고르면 응답에서 받은 `server.syncedAt` 을
`baseSyncedAt` 으로 넣어 다시 `PUT` 한다. 두 번째 요청은 통과한다.

**어느 쪽이 "최신"인지 서버가 판단하지 않는다.** `lastSeenAt` 이 더 큰 쪽을
자동으로 고르고 싶어지지만, 그 값은 클라이언트가 보낸 것이고 기기 시계는 틀릴 수
있다(명세 §5). 사람이 고르게 한다.

## 6. 서버는 세이브를 해석하지 않는다

**규칙은 클라이언트에 있다.** 서버는 받은 것을 보관하고 돌려줄 뿐이다.

- 스탯 감소도, 레벨업도, 코인 상한도 계산하지 않는다
- `save.version` 이 알 수 없는 값이어도 그대로 저장한다 — 옛 클라이언트가 새
  버전을 읽는 문제는 **클라이언트의 `save.ts` 가 이미 막고 있다**(미래 버전은
  로드 거부 후 백업). 서버가 한 번 더 막으면 새 버전을 배포할 때마다 서버도
  같이 배포해야 한다

다만 **컬럼으로 꺼낸 값(name·level·exp·coins)은 서버가 `state_json` 에서 뽑아
채운다.** 클라이언트가 따로 보내게 하면 두 값이 어긋날 수 있다.

검증은 형식만 한다: `save` 가 객체인가, 필수 필드가 있는가, 문자열 길이가 컬럼에
들어가는가. 값의 타당성(레벨 999 같은 것)은 보지 않는다 — 다음 절의 이유다.

## 7. 신뢰 경계 — 지금은 클라이언트를 믿는다

**이 단계에서는 세이브를 위조해도 남에게 피해가 없다.** 혼자 하는 게임이고
랭킹이 없다. 막으려는 시도는 전부 우회 가능하면서 코드만 복잡해진다(명세 §5).

**랭킹이나 친구 방문을 붙이는 순간 이 전제가 깨진다.** 그때는

- 미니게임 점수를 서버가 검증하거나 서버에서 계산해야 하고
- `lastSeenAt` 대신 **서버 시각**이 기준이 되어야 하며
- 이 API 는 그 설계에 맞춰 다시 그려야 한다

그러므로 **랭킹을 붙일 때 이 문서를 먼저 다시 읽는다.** 여기에 적힌 "믿는다"를
그대로 둔 채 랭킹만 얹으면 점수는 그날로 무의미해진다.

## 8. 에러 응답

기존 `GlobalExceptionHandler` 형식을 그대로 따른다 — 본문은 `{ "message": "..." }`
하나뿐이고, 충돌(409)만 `server` 를 더 싣는다.

**401 은 스프링 시큐리티의 기본값이 아니다.** 기본 진입점은 403 을 본문 없이
내는데, 프론트의 공용 클라이언트(`packages/api` 의 `client.ts`)는 **401 일 때만**
토큰을 지우고 로그인 화면으로 되돌린다. 403 이면 토큰이 만료된 사람은 로그인하라는
말도 못 듣고 요청이 조용히 실패하는 것만 본다 — 공용 기기에서는 앞사람의 만료된
토큰이 남아 있을 수 있어 특히 위험하다. `SecurityConfig` 에 진입점을 넣어 401 과
같은 본문 모양을 내게 한다. **이 변경은 보호된 경로 전부에 걸린다**(다른 게임 포함).

| 상황           | 코드 | message                              |
| -------------- | ---- | ------------------------------------ |
| 토큰 없음·만료 | 401  | 로그인이 필요합니다.                 |
| 저장된 펫 없음 | 404  | 저장된 펫이 없습니다.                |
| 충돌           | 409  | 다른 기기에 더 최근 진행이 있습니다. |
| 본문 형식 오류 | 400  | 세이브 형식이 올바르지 않습니다.     |

## 9. 클라이언트 계약 — `packages/api`

경로 문자열은 `packages/api` 한 곳에만 둔다(`auth.ts` 와 같은 이유 — 서버에서
경로를 바꿀 때 앱마다 찾아다니지 않기 위해서다).

```ts
export interface PetSyncResult {
  syncedAt: number
}

export interface PetConflict {
  server: { save: unknown; syncedAt: number }
}

export function createPetApi(client: ApiClient) {
  return {
    /** 없으면 null. 404 를 에러로 올리지 않는다 — 신규 사용자의 정상 상태다. */
    get: (): Promise<{ save: unknown; syncedAt: number } | null> => ...,
    /** 409 면 PetConflict 를 담은 에러를 던진다. 화면이 그것으로 선택지를 그린다. */
    put: (save: unknown, baseSyncedAt: number | null): Promise<PetSyncResult> => ...,
  }
}
```

`save` 를 `unknown` 으로 두는 것은 **`packages/api` 가 펫타운의 타입을 알면 안
되기 때문이다.** api 계층은 프레임워크·게임과 무관해야 한다(ARCHITECTURE.md 의
계층 표). 실제 타입은 `apps/pet` 이 받아서 자기 `save.ts` 로 검증한다 — 서버에서
온 값도 손상된 로컬 세이브와 똑같이 다뤄야 안전하다(`readServerSave`).

**구현하면서 달라진 것 둘.**

- **409 는 `PetConflictError` 로 던진다.** `ApiError` 를 상속하고 `server` 를 들고
  있어, 화면이 상태 코드를 다시 확인하지 않고 선택지를 그릴 수 있다. 본문 모양이
  아니면 그냥 원래 에러를 올린다 — 없는 값으로 카드를 그리느니 실패로 보이는 편이
  낫다.
- **`remove()` 를 함께 넣었다.** 2순위로 미룬 `DELETE /pet` 인데, 로그아웃이 그것과
  같은 경로를 쓰지 않더라도 자기 데이터를 지울 수단이 처음부터 있어야 한다(§12 의 2).

## 10. 클라이언트가 지켜야 할 것 — 공용 기기 전제

이 절은 **한 기기를 여러 사람이 번갈아 쓴다**는 전제에서 나온다(§2). 개인 기기만
생각하면 아래 규칙 대부분이 과해 보이지만, 공용 기기에서는 하나라도 빠지면
남의 진행이 사라진다.

### 서버가 정본, 로컬은 이 세션의 캐시

로그인하면 `GET /pet` 으로 받아 로컬에 쓰고, 그때부터 게임은 로컬로 돈다(스탯
계산은 매 프레임 도는 일이라 서버를 부를 수 없다). 로그아웃할 때 올린다.

### 세이브 키에 회원 id 를 넣는다

```
gj.pet.v1.<memberId>
```

**칸이 하나면 다음 사람이 앞사람을 덮어쓴다.** 키를 나누면 로그아웃이 늦거나
브라우저가 갑자기 죽어도 서로의 진행이 섞이지 않는다.

로그인 이전에 쓰던 익명 키(`gj.pet.v1`)는 **읽지 않는다.** 그 값이 누구 것인지
알 수 없기 때문이다. 남겨 두면 공용 기기에서 아무나 그 펫을 이어받게 된다.

### 로그아웃은 "올리고 지운다"

1. 서버에 올린다(`PUT /pet`)
2. 성공하면 그 회원의 로컬 키를 **지운다**
3. 올리지 못했으면 지우지 않고, 무엇이 남았는지 사용자에게 알린다

**올리기 전에 지우면 진행이 사라진다.** 반대로 지우지 않고 두면 다음 사람이
그 펫을 본다. 순서가 규칙이다.

### 자동 저장이 로그아웃 뒤에 되살리지 않게 한다

M1 에서 넣은 자동 저장은 `visibilitychange` 와 언마운트에서 마지막 상태를 쓴다.
**로그아웃 뒤에 그 경로가 한 번 더 돌면 방금 지운 키가 되살아난다.** 로그아웃은
저장 경로를 먼저 끄고 나서 지워야 한다.

### 기준 시각도 회원마다 적어 둔다

```
gj.pet.sync.v1.<memberId>
```

**로컬 세이브가 서버의 어느 시점에서 갈라져 나왔는지**를 적어 둔 값이다. 이것이
없으면 새로고침을 충돌과 구별할 수 없다 — 올리기는 30초마다라 마지막 몇십 초는
언제나 로컬에만 있는데, 그때마다 "어느 쪽을 쓸까요"를 묻게 된다.

로그인할 때의 판단은 이 표 하나다(`apps/pet/src/game/pet/sync.ts` 의 `reconcile`).

| 서버    | 로컬 | 기준 시각     | 한다                       |
| ------- | ---- | ------------- | -------------------------- |
| 없음    | 없음 | —             | 새 펫 (이름 입력)          |
| 없음    | 있음 | —             | 로컬로 계속, 나중에 올린다 |
| 있음    | 없음 | —             | 서버 것을 받는다           |
| 있음    | 있음 | 서버와 같음   | 로컬이 더 나중이다         |
| 있음    | 있음 | 다르거나 모름 | **묻는다**(§5)             |
| 못 만남 | 있음 | —             | 로컬로 계속                |
| 못 만남 | 없음 | —             | **다시 시도**              |

마지막 줄이 중요하다. **"못 만난 것"과 "없는 것"을 합치면** 서버가 잠깐 죽었을 때
모두가 신규 사용자로 보여 이름을 새로 짓게 되고, 한참 논 다음에야 충돌로 알게 된다.

### 동기화 실패가 플레이를 막으면 안 된다

서버가 죽어 있어도 이미 로그인한 세션은 로컬로 계속 돌아간다. 실패는 조용히
넘기지 말되 화면을 막지도 않는다 — 저장 실패 배너(M1)와 같은 방식으로 알린다.
다만 **로그아웃 시의 실패는 다르다.** 그때는 올리지 못한 것을 분명히 알려야
한다(위 3번).

### 올리는 시점

로그아웃 때는 반드시, 그 밖에는 자동 저장과 같은 자리(주기적 틱과
`visibilitychange` hidden)에서 올린다. 행동마다 올리면 요청이 쏟아지고,
로그아웃 때만 올리면 브라우저가 갑자기 죽었을 때 그 세션이 통째로 날아간다.

## 11. 배포에 필요한 설정

| 항목                  | 값                                                                     |
| --------------------- | ---------------------------------------------------------------------- |
| 서버 `CORS_ORIGINS`   | 펫타운 Vercel 도메인을 **추가**해야 한다                               |
| 펫 앱 `VITE_API_BASE` | `https://game-api.oijwef098234.com` (기본값은 `http://localhost:8090`) |

CORS 목록에 없으면 브라우저가 요청을 막는데, 그 실패는 서버 로그에 남지 않아
원인을 찾는 데 시간이 오래 걸린다. **배포 전에 먼저 넣는다.**

## 12. 열린 질문

1. **기관 환경에서 계정을 누가 만드는가.** 이용자가 직접 가입하는가, 관리자가
   미리 만들어 주는가에 따라 첫 화면이 달라진다. 비밀번호를 잊었을 때의 문제(3번)도
   여기에 걸린다.
2. ~~**`DELETE /pet` 을 첫 구현에 넣을 것인가.**~~ 넣었다. 서버·클라이언트 양쪽에
   있다.
3. **비밀번호를 잊었을 때.** 기존 회원 체계에 재설정 경로가 없다. 펫타운은
   진행이 걸려 있어 다른 게임보다 무거운 문제이고, **공용 기기라 "기기에 로그인이
   남아 있으니 괜찮다"는 탈출구도 없다.**
4. **자리를 뜨고 로그아웃을 잊은 경우.** 다음 사람이 앞사람 계정으로 계속 놀게
   된다. 일정 시간 조작이 없으면 자동 로그아웃할 것인가, 그렇다면 그 시간은
   얼마인가.
