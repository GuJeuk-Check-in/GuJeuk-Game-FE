# 펫타운 명세서

구즉 미니게임에 붙일 **펫 육성 게임**의 설계 문서. 구현 전에 규칙과 수치를
먼저 못 박아 두기 위한 것이다. 코드보다 이 문서가 먼저다.

- 상태: 초안 (구현 시작 전) — 도트는 AI 생성으로 확정 (§12)
- 앱 slug: `pet` / 워크스페이스 `@gujuck/pet` / 포트 5174 / CSS 접두사 `pt-`
- 참조: [ARCHITECTURE.md](ARCHITECTURE.md), [CONVENTIONS.md](CONVENTIONS.md)

## 1. 왜 이 게임은 기존 4개와 다른가

지금 레포의 게임(틱택토·알까기·양궁)은 전부 **한 판이 끝나면 상태가 사라지는
대전 게임**이다. 서버가 방을 들고 있고, 결과는 레이팅 숫자 하나로 남는다.

펫타운은 정반대다.

|             | 기존 게임      | 펫타운                |
| ----------- | -------------- | --------------------- |
| 상태 수명   | 한 판 (수 분)  | 영구 (수 개월)        |
| 상대        | 사람           | 없음 (혼자)           |
| 서버 역할   | 진행의 주인    | 백업 (2단계)          |
| 세션        | 길고 드묾      | 짧고 잦음 (1~3분)     |
| 망가지는 법 | 한 판이 꼬인다 | **세이브가 날아간다** |

이 차이가 설계의 모든 것을 결정한다. 특히 마지막 줄 — 대전 게임은 버그가 나도
다시 시작하면 되지만, 육성 게임은 3주 키운 펫이 사라지면 그 사람은 돌아오지
않는다. 그래서 이 문서는 **세이브·시간 경과·마이그레이션**에 가장 많은 지면을
쓴다. 재미보다 먼저 안 깨지는 것이 요구사항이다.

## 2. 게임 한 줄 요약

> 도트로 그려진 펫 한 마리를 방 여섯 개짜리 집에서 먹이고 씻기고 재우며,
> 미니게임으로 코인을 벌어 집을 꾸미고 레벨을 올린다.

포우(Pou)의 구조를 따른다. 진화 분기도, 전투도, 다른 사람도 없다.
**"오늘 잠깐 들러서 밥 주고 한 판 하고 나간다"**가 한 세션의 전부다.

## 3. 화면 구조

세로 고정(9:16). 모바일 우선이고 데스크톱에서는 좌우 레터박스로 둔다.
가로 대응은 하지 않는다 — 방 배경 도트를 두 벌 그려야 하고, 이 게임은 한
손으로 하는 게임이다.

```
┌─────────────────────┐
│ Lv.7        코인 320│  HUD (React)
│ 밥 ▓▓▓▓░  기분 ▓▓▓░░│
├─────────────────────┤
│                     │
│   ◀   [ 방 화면 ]  ▶ │  Canvas (도트)
│         펫          │
│                     │
├─────────────────────┤
│  [ 먹이주기 ] [가방] │  액션 바 (방마다 다름, React)
└─────────────────────┘
```

방은 좌우 화살표 또는 스와이프로 이동한다. 첫 버전의 방은 6개다.

| 방     | 하는 일                           | 해금           |
| ------ | --------------------------------- | -------------- |
| 거실   | 기본 화면. 펫 쓰다듬기, 가구 배치 | 처음부터       |
| 주방   | 인벤토리의 음식 먹이기            | 처음부터       |
| 욕실   | 문질러서 씻기기                   | 처음부터       |
| 침실   | 재우기 (에너지 실시간 회복)       | 처음부터       |
| 놀이터 | 미니게임 3종 진입                 | 튜토리얼 4단계 |
| 상점   | 음식·가구 구매                    | 튜토리얼 5단계 |

## 4. 스탯

4개, 각각 0~100의 실수. 화면에는 정수로 반올림해 보여준다.

| 스탯           | 시간당 감소        | 0이 되면                                |
| -------------- | ------------------ | --------------------------------------- |
| 배고픔(포만감) | 6.0                | 코인 획득 50%, EXP 획득 0               |
| 기분           | 4.0                | EXP 획득 0, 펫이 `sad` 애니메이션       |
| 청결           | 3.0                | 파리가 붙고 기분 감소가 시간당 2.0 추가 |
| 에너지         | 2.0 (수면 중 회복) | 미니게임 진입 불가 (재워야 함)          |

**펫은 죽지 않는다. 가출하지도 않는다.** 스탯은 0에서 멈추고, 벌칙은
"코인이 덜 벌리고 시무룩해 있다"까지다. 되돌릴 수 없는 상실은 캐주얼 육성
게임의 이탈 사유 1순위다. 방치의 대가는 손해지 처벌이 아니다.

수치 근거: 포만감 100에서 0까지 약 16.7시간이다. **하루 한 번 들르면 유지되고,
이틀을 비우면 눈에 띄게 나빠지는** 페이스를 목표로 잡았다. 만든 뒤 "하루 한 번이
부담스럽다"는 반응이 나오면 감소율만 조정한다(밸런싱 상수는 `economy.ts` 한 곳에
모은다).

### 회복 수단

| 행동     | 효과                           | 비용   | EXP           |
| -------- | ------------------------------ | ------ | ------------- |
| 사과     | 포만감 +15                     | 10코인 | +8            |
| 빵       | 포만감 +35                     | 25코인 | +8            |
| 케이크   | 포만감 +70, 기분 +10           | 60코인 | +12           |
| 씻기기   | 청결 100                       | 무료   | +6            |
| 쓰다듬기 | 기분 +5 (하루 5회까지)         | 무료   | +2            |
| 재우기   | 에너지 시간당 +25 (최대 8시간) | 무료   | +10 (기상 시) |

**과식·과잉 청소로는 EXP가 나오지 않는다.** 포만감 90 이상에서 먹이거나 청결
70 이상에서 씻기면 스탯만 오르고 EXP는 0이다. 이 조건이 없으면 사과를 연타하는
것이 최적 전략이 되어 게임이 사라진다.

수면 중에는 배고픔·기분·청결 감소가 절반이다. 잠든 사이 굶어 있으면 재우는
행동 자체가 손해가 되어 아무도 재우지 않는다.

## 5. 시간 경과 — 이 게임에서 제일 조심할 부분

실시간으로 흐른다. 껐다 켜면 그동안의 경과가 반영된다.

```
elapsed = now - lastSeenAt
if (elapsed < 0) elapsed = 0            // 기기 시계가 되돌아간 경우
elapsed = min(elapsed, 12시간)          // 상한
```

**상한 12시간을 두는 이유.** 2주 만에 돌아온 사람에게 텅 빈 게이지와 시무룩한
펫을 보여주면 그 사람은 그대로 앱을 지운다. 최악의 경우에도 포만감은
100 → 28로만 떨어진다(6 × 12 = 72). 밥 한 번이면 복구되는 수준이다.

**복귀 화면.** 4시간 이상 비웠다가 돌아오면 경과 요약 카드를 띄운다.
"12시간 만이야!" + 줄어든 스탯 + (자고 있었다면) 회복된 에너지. 무슨 일이
있었는지 알려주지 않으면 사용자는 게이지가 왜 줄었는지 모른다.

**치트에 대해.** 로컬 저장이므로 기기 시계를 돌리거나 localStorage를 직접
고치는 것은 전부 가능하다. **1단계에서는 막지 않는다** — 랭킹이 없으니 남에게
피해가 없고, 막으려는 시도는 전부 우회 가능하면서 코드만 복잡해진다. 랭킹이나
친구 방문을 붙이는 순간(3단계) **서버 시각과 서버 검증이 전제**가 된다. 그때
클라이언트 값을 그대로 믿는 API를 만들면 안 된다.

## 6. 레벨과 성장

EXP는 돌봄과 미니게임에서 나온다. 레벨업에 필요한 EXP는 선형이다.

```
필요EXP(n) = 100 + 60 × (n - 1)     // Lv1→2는 100, Lv9→10은 580
```

10레벨까지 누적 약 3,600 EXP. 하루 평균 획득량을 80~120으로 잡으면 **약 한 달에
10레벨**이다. 지수 곡선을 쓰지 않는 이유는 후반 구간이 벽이 되면 결국 방치
게임이 되기 때문이다.

레벨업 보상: 코인 `50 × 레벨`, 그리고 아래 외형 단계 변화.

| 단계   | 레벨 | 변화                            |
| ------ | ---- | ------------------------------- |
| 아기   | 1~4  | 작고 머리가 크다                |
| 어린이 | 5~9  | 비율이 잡히고 움직임이 빨라진다 |
| 어른   | 10+  | 가장 큼                         |

**외형만 바뀌고 능력 차이는 없다.** 분기도 없다. 분기를 넣는 순간 도트
리소스가 (단계 × 분기)로 늘어나는데, 이 프로젝트의 최대 리스크는 코드가 아니라
그림이다(§12 참조).

## 7. 재화

**코인 하나만 쓴다.** 두 번째 재화(젬 등)는 결제를 붙일 때나 의미가 있다.

획득처:

- 미니게임 (§8)
- 일일 첫 접속 +30
- 레벨업 `50 × 레벨`
- 튜토리얼 완료 +100

**하루 코인 상한 300 (미니게임 합산).** 상한이 없으면 반복 플레이로 상점이
하루 만에 소진되고, 그다음 날부터 살 게 없어진다. 상한은 자정(로컬 시각) 기준
초기화하고, 도달하면 "오늘은 충분히 놀았어" 문구로 알린다. 조용히 0코인을 주면
버그로 오해한다.

에너지 예산과 상한이 맞물린다. 에너지 100에서 미니게임 한 판이 8~12이므로
**깨어 있는 동안 8판 남짓** 가능하고, 8판이면 코인 상한에 대략 닿는다. 두
시스템이 서로를 강제하지 않고 같은 답을 가리키게 맞춘 것이다.

## 8. 미니게임 3종

전부 펫이 직접 등장한다. **matter.js를 쓰지 않는다** — 세 게임 모두 사각형
겹침 판정(AABB)만 필요한데, 물리 엔진은 번들에 230KB를 얹고 도트 게임에
아무것도 더해주지 않는다. 충돌 판정은 앱 안에 직접 쓴다.

### 8.1 간식받기

- 펫이 화면 하단. 드래그(또는 좌우 탭)로 이동.
- 위에서 떨어지는 것: 음식 +1, 황금 도넛 +5, 폭탄 → 라이프 -1
- 라이프 3. 낙하 속도는 10초마다 12% 증가.
- 종료: 60초 경과 또는 라이프 소진
- 점수 = 획득 합 / **코인 = 점수 × 1** / EXP = 10 + 점수/5 / 에너지 -12

### 8.2 폴짝 달리기

- 원버튼. 탭하면 점프, 길게 누르면 더 높이(최대 0.35초까지 반영).
- 장애물: 낮은 것·높은 것·낮게 나는 새 3종을 랜덤 배치. 직전 장애물과의 최소
  간격은 현재 속도에서 점프 한 번이 반드시 성립하는 거리로 잡는다.
  **클리어 불가능한 배치가 나오면 안 된다.**
- 속도는 초당 1.5% 증가, 2.5배에서 상한.
- 종료: 충돌 1회 즉시
- 점수 = 달린 거리(m) / **코인 = floor(m / 10)** / EXP = 10 + m/50 / 에너지 -12

### 8.3 따라하기

- 4색 타일. 라운드마다 패턴이 1개씩 길어진다. 라운드 5부터 재생 속도 가속.
- 종료: 한 번 틀리면 즉시
- 점수 = 도달 라운드 / **코인 = 라운드 × 3** / EXP = 5 + 라운드 × 2 / 에너지 -8

세 게임 모두 잘하면 30~50코인이 나오도록 계수를 잡았다. 실제 플레이로 측정한
값이 아니라 설계값이므로, 만든 뒤 각자 10판씩 돌려 보고 조정한다. 그때 바꾼
근거는 상수 옆 주석에 남긴다([CONVENTIONS](CONVENTIONS.md)의 주석 규칙).

## 9. 튜토리얼

첫 실행에서만 뜬다. 7단계이고, 각 단계는 **조건이 충족되어야** 넘어간다. 읽고
넘기는 안내가 아니라 실제로 해 보게 만드는 방식이다.

| #   | 내용                                                    | 넘어가는 조건 |
| --- | ------------------------------------------------------- | ------------- |
| 0   | 알이 흔들린다. 탭해서 부화                              | 탭            |
| 1   | 이름 짓기 (1~8자)                                       | 확정          |
| 2   | 배고픔 게이지 강조 → 주방 → 사과 먹이기 (사과 3개 지급) | 포만감 상승   |
| 3   | 청결 게이지 → 욕실 → 문질러 씻기                        | 청결 100      |
| 4   | 놀이터 해금 → 간식받기 1판                              | 게임 종료     |
| 5   | 상점 해금 → 아무거나 1개 구매                           | 구매 성공     |
| 6   | 침실 설명 (지금 재울 필요는 없음)                       | 확인          |

- 튜토리얼 판은 **에너지를 소모하지 않고 코인 100을 보장한다.** 첫 판에서 0점을
  받고 살 게 없어지면 5단계에서 막힌다.
- 스킵 버튼은 2단계부터 노출한다. 0~1단계(부화·이름)는 건너뛸 수 없다.
- **진행 단계를 세이브에 기록한다.** 3단계에서 앱을 끄면 3단계부터 재개한다.
- 설정에서 다시 보기 가능.

구현은 순수 상태 머신(`tutorial.ts`)으로 둔다. 각 단계는
`{ id, 하이라이트 대상, 말풍선, 완료조건(state) => boolean }`이고, 완료 조건은
게임 상태만 보는 순수 함수다. 이렇게 두면 **튜토리얼이 UI를 몰라도 되고**, 버튼
위치를 바꿔도 튜토리얼이 깨지지 않는다. 오버레이는 하이라이트 대상 외의 입력을
막는 것만 한다.

## 10. 세이브

localStorage 키 `gj.pet.v1`. 값은 JSON 한 덩어리.

```ts
interface PetSave {
  version: 1
  pet: { name: string; bornAt: number; level: number; exp: number }
  stats: { hunger: number; mood: number; clean: number; energy: number }
  wallet: { coins: number }
  inventory: Record<ItemId, number>
  room: { wallpaper: ItemId; floor: ItemId; placed: { item: ItemId; x: number; y: number }[] }
  sleep: { since: number } | null
  tutorial: { step: number; done: boolean }
  daily: { date: string; coinsEarned: number; checkedIn: boolean } // date는 YYYY-MM-DD 로컬
  lastSeenAt: number
}
```

**저장 시점**: 상태가 바뀌는 모든 행동 직후 + 30초마다 + `visibilitychange`가
hidden이 될 때. 모바일 브라우저는 탭을 백그라운드로 보낸 뒤 예고 없이 죽이므로
`beforeunload`만 믿으면 안 된다.

**마이그레이션**: `version`으로 분기한다. 읽은 버전이 코드보다 **높으면**(다른
기기에서 최신 버전을 쓴 경우) 로드를 거부하고 원본을 `gj.pet.backup.<ts>`로 옮긴
뒤 새로 시작한다. 미래 버전을 옛 코드로 해석해서 덮어쓰는 것이 세이브를 날리는
가장 흔한 경로다.

**손상 대응**: JSON 파싱 실패나 필수 필드 누락이면 같은 방식으로 백업 후 새로
시작하고, 사용자에게 "저장 파일을 읽지 못했어요. 백업은 남겨 두었습니다"를
알린다. 조용히 초기화하면 안 된다.

## 11. 코드 구조

레포 규칙을 그대로 따른다. 생성은 스크립트로 한다.

```bash
yarn create:app pet "펫타운" --canvas
```

- 팔레트 16색 고정.

## 12. 도트 리소스 — AI 생성 파이프라인

**결정: AI로 생성한다.** 다만 AI 픽셀아트에는 피할 수 없는 약점이 하나 있고,
이 절의 설계는 전부 그 약점을 우회하기 위한 것이다.

### 문제: AI는 같은 캐릭터를 두 번 그리지 못한다

"우리 펫의 idle 4프레임"을 프롬프트로 네 번 뽑으면 **네 마리의 다른 펫**이
나온다. 눈 위치가 1픽셀씩 밀리고 색이 미묘하게 달라진다. 32×32에서 1픽셀은
전체의 3%다. 이걸 붙여서 애니메이션으로 돌리면 캐릭터가 부들부들 떨린다.

그러므로 **AI에게 애니메이션 프레임을 시키지 않는다.**

### 해법: AI는 "기본 모습" 한 장만, 나머지는 코드가 만든다

AI는 성장 단계당 **정지 이미지 1장**만 만든다. 표정 변화는 32×32 위에서 직접
찍고(눈 감기는 픽셀 6개다), 움직임은 코드가 만든다.

| 만드는 주체   | 대상                                            |
| ------------- | ----------------------------------------------- |
| AI 생성       | 펫 기본 모습 3장, 방 배경 6장, 아이템·가구 32개 |
| 손 · 스크립트 | 표정 오버레이 (눈 감음 · 입 벌림 · 처진 눈썹)   |
| 코드          | 모든 움직임 (§12.3)                             |

이렇게 하면 **생성 이미지가 캐릭터당 1장이므로 일관성 문제가 성립하지 않는다.**
프레임 사이에 흔들릴 원본이 애초에 없다.

### 12.0 펫 컨셉과 팔레트

**펫은 종족이 없는 둥근 생명체다.** 강아지도 고양이도 아니고, 귀도 꼬리도 다리도
없다. 몸 전체가 하나의 연속된 실루엣이고 넓은 밑면으로 바닥에 그대로 앉는다.
실루엣이 단순할수록 축소가 깨끗하고, 표정 오버레이 3종(눈 감음 · 입 벌림 ·
처진 눈썹)만으로 감정이 다 전달된다. 성장 3단계도 새 형태가 아니라 **크기와
머리 비율**로만 표현한다 — 아기는 작고 머리가 크며, 어른은 크고 비율이 잡힌다.

귀와 꼬리를 뺀 것은 취향이 아니라 제약이다. 64×64에서 귀는 6~8픽셀이고, 그
크기의 가는 돌출부는 축소 과정에서 형태가 흔들려 프레임마다 다르게 남는다.
더 큰 이유는 **성장 단계를 형태가 아니라 비율로 표현**하기로 했다는 것이다.
돌출부가 있으면 단계마다 그 돌출부까지 따로 맞춰야 한다.

**팔레트는 공개 16색 팔레트(Vanilla Milkshake)를 그대로 쓴다.** 직접 16칸을 짜면
명도 관계를 잘못 잡아 배경과 펫이 붙어 보이기 쉬운데, 공개 팔레트는 대비와
명도 분포가 이미 검증되어 있다. 펫 색을 팔레트에 맞추지, 팔레트를 펫에
맞추지 않는다.

정확한 16개 색값은 Step 1에서 원본 출처에서 그대로 옮겨 `palette.ts`에 박고,
기억이나 짐작으로 적지 않는다. 한 색이라도 틀리면 양자화 결과가 미묘하게
어긋나는데 눈으로는 원인을 못 찾는다.

### 12.1 생성 규격

생성 모델은 **z_image**로 정한다. 무료 플랜에서 쓸 수 있고 장당 0.15 크레딧이다
(Recraft V4.1이 팔레트·배경색을 직접 지정할 수 있어 더 적합하지만 유료 플랜 전용이다).
출력 크기는 모델이 정하며, 요청한 비율에 따라 아래로 고정된다.

| 항목              | 생성 (z_image) | 최종 크기   | 축소 비율 | 수량        |
| ----------------- | -------------- | ----------- | --------- | ----------- |
| 펫 기본 모습      | 2048×2048      | **128×128** | 16 : 1    | 3           |
| 표정 오버레이     | (생성 안 함)   | 128×128     | —         | 3종 × 3단계 |
| 방 배경           | 1152×2048      | 360×640     | 3.2 : 1   | 6           |
| 음식 · 아이템     | 2048×2048      | **48×48**   | 43 : 1    | 12          |
| 가구              | 2048×2048      | 48~96       | —         | 10          |
| 미니게임 오브젝트 | 2048×2048      | 48×48       | 43 : 1    | 10          |

크게 뽑아서 줄이는 이유: AI에게 32×32를 직접 시키면 "픽셀아트처럼 보이는
안티에일리어싱된 그림"이 나온다. 도트가 아니라 도트 흉내다. 큰 그림을 정직하게
축소하는 편이 결과가 깨끗하다.

**크기는 두 번 올렸고 두 번 다 실측이 근거다.**

초안은 방 180×320 · 펫 32×32 · 아이템 16×16이었다. 첫 실측에서 16×16 사과가 둥근
덩어리로 뭉개졌고(24×24에서 꼭지 홈까지 살아났다), 32×32 펫을 180×320 방에 세우니
주인공이 아니라 소품으로 보였다. 두 번째로, 그 결과를 놓고 "화질이 낮다"는 판단이
나와 논리 해상도를 통째로 2배로 올렸다. 지금 값이 그 결과다.

해상도를 올리면 축소 비율이 함께 완화되어(방 6.4:1 → 3.2:1, 펫 64:1 → 16:1) 선과
눈이 훨씬 깨끗하게 남는다. 대신 소스의 미세한 텍스처가 평균에 묻히지 않고 점으로
드러난다 — 그래서 §12.2에 5번 단계가 생겼다.

### 12.2 후처리 (`apps/pet/tools/pixelize.mjs`)

생성 이미지는 그대로 쓸 수 없다. 아래 순서로 통과시킨다. **1번과 4번은 초안에
없던 단계이고, 실제로 돌려 본 뒤에 추가되었다** (근거는 §12.5).

1. **누끼** — 전용 배경 제거 도구로 알파를 딴다. 스크립트는 입력 알파를 신뢰하고,
   알파가 전부 불투명이면 "배경이 제거되지 않았다"고 알린다.
   프롬프트로 단색 배경을 요구하는 크로마키 방식은 폐기했다 — 모델이 그 지시를
   따르지 않는다(§12.5).
2. **면적 가중 축소** — 각 출력 픽셀이 덮는 소스 영역의 가중 평균. 배수가 정수가
   아니어도 된다. **감마 보정이 필수다**: sRGB 값을 그대로 평균하면 결과가 어두워지고
   탁해진다. 선형 광량으로 바꿔 평균한 뒤 되돌린다. 알파는 premultiply한 뒤 평균하고,
   도트에는 반투명이 없으므로 0.5에서 이진화한다.
3. **팔레트 양자화** — 고정 16색 중 가장 가까운 색으로 스냅한다. 거리는 OKLab에서
   잰다. 이 단계가 전체 에셋의 톤을 강제로 통일한다. **AI 생성물이 한 세트처럼
   보이게 만드는 것은 프롬프트가 아니라 이 양자화다.**
   에셋마다 **쓸 색을 부분집합으로 제한할 수 있어야 한다** — 16색 전체로 스냅하면
   색상이 표류한다(민트 그린 몸통이 형광 하늘색이 되었다).
4. **외곽선 재부착** — 축소된 실루엣 바깥 1px를 팔레트의 가장 어두운 색으로 채운다.
   축소 비율이 크면 소스의 굵은 외곽선이 평균에 녹아 사라지기 때문이다(§12.5).
5. **외톨이 점 제거**(선택) — 자기 색과 같은 이웃이 하나도 없는 1px를 이웃 다수색으로
   덮는다. 해상도를 2배로 올린 뒤 소스의 미세한 텍스처가 평균에 묻히지 않고 벽·바닥에
   점으로 흩뿌려졌다. 낮은 해상도에서는 없던 문제다. 의도된 1px 점(눈 하이라이트)을
   지울 위험이 있으므로 **기본은 꺼 두고 필요한 에셋에만 켠다.**

**"정수배"는 화면 확대에만 해당한다.** 초안에는 축소도 정수배여야 격자가 어긋나지
않는다고 적었는데 그건 틀렸다. 면적 가중 평균은 각 출력 픽셀이 자기가 덮는 소스
영역만 보므로 배수가 3.2여도 격자가 어긋나지 않는다. 정수배가 반드시 필요한 곳은
결과를 화면에 확대해 띄울 때다.

팔레트는 `apps/pet/src/game/palette.ts` 한 곳에 두고, 스크립트와 게임 코드가
같은 배열을 읽는다. 두 벌로 갈리면 렌더링 색과 에셋 색이 어긋난다.

### 12.3 코드가 만드는 움직임

정적 스프라이트 + 오버레이만으로 아래를 전부 만든다.

| 상태  | 구현                                                  |
| ----- | ----------------------------------------------------- |
| idle  | sin파로 1~~2px 상하 + 3~~5초마다 눈 깜빡임(2프레임)   |
| walk  | 좌우 이동 + 상하 바운스 + 착지 시 세로 1px 스쿼시     |
| eat   | 입 벌림 오버레이 토글 + 음식 스프라이트가 입으로 이동 |
| wash  | 좌우 1px 진동 + 거품 파티클                           |
| sleep | 눈 감음 오버레이 + 느린 호흡(2px 스쿼시) + Zzz 파티클 |
| sad   | 처진 눈썹 + 1px 아래로 + 느린 좌우 흔들림             |
| happy | 짧은 점프 2회 + 하트 파티클                           |

**회전과 비정수 스케일은 금지한다.** 도트를 뭉갠다. 스쿼시·스트레치는 정수
픽셀(128×128 기준 2~8px)로만 한다.

파티클(거품·하트·Zzz)은 4×4 도트 하나를 재사용해 코드로 뿌린다. 새 에셋이
필요 없고, 화면이 가장 살아 보이는 값싼 방법이다.

### 12.4 검증 먼저

**M1 코드를 쓰기 전에 이 파이프라인부터 확인한다.** 펫 1마리 · 방 1개 ·
아이템 1개를 실제 화면 배율로 띄워 보고, 도트가 깨끗하고 색이 팔레트 안에
있는지 본다. 여기서 실패하면 에셋 구매나 직접 그리기로 방향을 바꿔야 하는데,
그 판단은 게임 코드를 쓰기 전에 내려야 싸다.

### 12.5 실측 기록 — 축소 비율이 선 두께를 정한다

파이프라인을 실제로 돌려서 확인한 것이다. 나중에 "왜 이렇게 복잡한가"를 다시
묻지 않기 위해 남긴다.

**프롬프트로 단색 배경을 얻지 못했다.** "plain solid magenta background"를
넣었지만 모델은 부드러운 분홍 그라데이션을 그렸다. 네 모서리 색이 전부 다르고
소스 고유색이 46,368개였다. 크로마키는 사과의 붉은 하이라이트에 구멍을 냈을
것이다. 전용 누끼 도구로 바꾸자 투명 76.5% / 불투명 10.8%로 깨끗하게 떨어졌다.

**같은 파이프라인이 방에서는 성공하고 펫에서는 실패했다.** 원인은 축소 비율이다.

| 에셋   | 축소 비율 | 소스 외곽선 20px → | 결과                 |
| ------ | --------- | ------------------ | -------------------- |
| 방     | 6.4 : 1   | 3px                | 외곽선이 살아남는다  |
| 펫     | 64 : 1    | 0.3px              | 평균에 녹아 사라진다 |
| 아이템 | 128 : 1   | 0.15px             | 사라진다             |

외곽선을 잃은 펫은 물 빠진 하늘색 덩어리가 되어 도트로 읽히지 않았다.
**이건 프롬프트로 고쳐지지 않는다** — "더 굵은 외곽선"을 요구해도 비율이
그대로면 같은 일이 일어난다. 그래서 축소 뒤에 외곽선을 직접 그려 넣는다.

위 표의 측정은 펫을 32×32로 뽑았을 때의 것이다. 최종 크기를 128×128로 올리면
비율이 16:1이 되어 조건이 나아지지만, 그 상태에서 외곽선 재부착을 빼고 다시
재보지는 않았다. 재부착 단계는 그대로 둔다 — 빼서 얻는 것이 없다.

최종 크기·최종 팔레트로 다시 뽑은 결과:

| 에셋       | 고유색 | 팔레트 밖 | 반투명 | 제거된 점 |
| ---------- | ------ | --------- | ------ | --------- |
| 펫 128×128 | 9      | 0         | 0      | 161       |
| 사과 48×48 | 4      | 0         | 0      | —         |
| 방 360×640 | 10     | 0         | 0      | 310       |

세 장을 한 화면에 합성해 보면 외곽선 두께와 색 언어가 같아 **한 세트로 보인다.**
§12.4의 합격 기준을 만족한다.

### 12.7 팔레트를 Sweetie 16에서 Vanilla Milkshake로 바꿨다

첫 에셋을 실제로 보고 나서 "색이 너무 강렬해 촌스럽다"는 판단이 나왔다. 형광에
가까운 하늘색 펫과 강한 주황 바닥이 원인이었다.

감으로 고르지 않고 **채도를 재서** 골랐다. lospec의 16색 팔레트 후보 11개를 받아
각 색을 OKLab으로 옮기고 평균 채도(a·b 평면의 거리)를 계산했다.

| 팔레트                | 평균 채도 | 최대 채도 | 명도 폭 |
| --------------------- | --------- | --------- | ------- |
| Steam Lords           | 0.047     | 0.071     | 0.665   |
| Fantasy 16            | 0.072     | 0.146     | 0.845   |

숫자만으로 정하지는 않았다. **같은 원본을 후보 6개로 각각 양자화해 나란히 놓고**
골랐다. 채도가 가장 낮은 Steam Lords는 펫이 회백색이 되어 기르고 싶은 느낌이
사라졌고, Antiquity 16은 펫이 크림색이 되어 배경과 섞였다. Vanilla Milkshake는
전체를 눅이면서도 펫의 민트 정체성을 유지한 유일한 후보였다.

**팔레트를 재양자화하는 데는 이미지 생성 비용이 들지 않는다.** 원본을 보관해 두면
팔레트는 언제든 바꿔 볼 수 있다. 그래서 `tools/raw/`의 원본을 지우지 않는다.

**이 팔레트의 제약**: 명도 0.6 미만이 두 색뿐이라 어두운 음영을 넣을 색이 없다.
형태는 명암 그라데이션이 아니라 외곽선이 지탱한다. 에셋을 그릴 때 이걸 먼저 알고
시작해야 한다.

### 12.8 여러 개는 한 장에 그려서 잘라 쓴다

**누끼가 생성보다 6배 비싸다.** 생성은 장당 0.15 크레딧인데 배경 제거는 1.0 이다.
아이템 12개를 한 장씩 뽑으면 13.8 크레딧이지만, 한 장에 12개를 그려 배경을 한 번만
지우고 잘라 쓰면 1.15 로 끝난다.

그런데 **비용보다 품질 쪽 효과가 더 컸다.** 축소 비율이 선 두께를 정하는데(§12.5),
물건 하나를 2048²로 뽑아 48px로 줄이면 43:1 이지만 시트에서 한 칸이 약 370px 이면
7.7:1 이다. 실제로 단독으로 뽑은 사과보다 시트에서 잘라낸 사과가 눈에 띄게 선명해서,
`src/assets/item-apple.png` 를 시트 쪽으로 교체했다.

|                  | 한 장씩     | 시트                                  |
| ---------------- | ----------- | ------------------------------------- |
| 아이템 12개 비용 | 13.8 크레딧 | 1.15 크레딧 (배경 제거가 무료면 0.15) |
| 축소 비율        | 43 : 1      | 7.7 : 1                               |
| 스타일 일관성    | 장마다 다름 | 같은 그림에서 나옴                    |

### 12.9 배경 제거는 먼저 공짜로 시도한다

시트를 뽑아 보니 배경이 아주 평평했다 — 테두리 픽셀의 최대 채널 편차가 8이었다.
이 정도면 **테두리에서 번져 나가는 flood fill** 로 지울 수 있고, 실제로 74.7% 를
지워 물건 11개가 정확히 분리됐다. 유료 누끼를 쓰지 않았다.

**고정색 크로마키와 다르다.** 색만 보고 지우면 물건 안쪽의 배경과 비슷한 색(우유갑의
옅은 하늘색)에 구멍이 뚫린다. 테두리에서 이어진 픽셀만 지우면 굵은 외곽선이 벽
역할을 해서 안쪽이 지켜진다.

그래서 순서는 이렇다.

1. `slice.mjs --drop-background` 를 먼저 시도한다. 스크립트는 지운 비율을 보고하고,
   너무 적거나(10% 미만) 너무 많으면(97% 초과) 실패로 죽는다.
2. 실패하면 그때 유료 누끼 도구를 쓴다. §12.5 처럼 배경이 그라데이션으로 나온
   경우가 그렇다.

이 덕분에 남은 에셋 47점의 예상 비용이 **약 41 크레딧에서 약 1.2 크레딧으로** 줄었다.

### 12.10 잘라내기는 격자가 아니라 덩어리로 한다

생성 모델은 격자를 정확히 지키지 않는다. 4×3 격자로 12개를 요구했더니 **11개를
그렸다**(당근이 감귤이 되고 생선은 빠졌다). 좌표로 자르면 전부 어긋난다.

그래서 알파가 이어진 덩어리(연결 성분)를 찾아 그 경계 상자로 자른다. 설계에서
중요한 것 네 가지:

- **8-이웃으로 잇는다.** 4-이웃만 쓰면 사과 꼭지처럼 대각선으로만 닿은 획이 별개
  덩어리로 떨어진다.
- **자기 덩어리의 픽셀만 복사한다.** 경계 상자를 통째로 잘라내면 상자 안으로 삐져
  들어온 옆 물건의 조각이 따라온다.
- **모든 조각을 같은 크기의 캔버스에 담는다.** 각자 제 경계 상자로 자른 뒤 전부
  48×48 로 줄이면 사탕과 케이크가 같은 크기가 된다. 공통 캔버스에 담으면 뒤에서
  같은 배율이 걸려 상대 크기가 지켜진다.
- **이름 개수와 덩어리 수가 다르면 죽는다.** 앞에서부터 조용히 붙이면 이름과 그림이
  어긋난 채로 전부 저장되고, 그 어긋남은 게임에 넣고 나서야 눈에 띈다.

### 12.6 프롬프트에서 부정문을 쓰지 마라

펫 첫 생성에서 `no legs, no feet`를 넣었는데 **다리가 달린 펫이 나왔다.** 이미지
모델에게 부정 표현은 그 단어를 지우는 지시가 아니라 그 단어를 화면에 불러오는
지시에 가깝다.

두 번째 시도에서 다리·발이라는 단어를 아예 빼고, 원하는 형태를 긍정문으로만
서술했다 — "몸 전체가 하나의 연속된 조약돌 형태", "넓고 둥근 밑면이 바닥에
그대로 닿는다", "밑면을 따라 끊기지 않는 외곽선". 한 번에 의도대로 나왔다.

배경도 같은 함정이었다. `no shadow`를 넣었지만 그림자 타원이 그려졌다. 다만
이건 누끼 단계에서 피사체가 아닌 것으로 함께 제거되어 문제가 되지 않았다.

**앞으로 에셋 프롬프트를 쓸 때는 "없어야 하는 것"을 나열하지 말고 "있어야 하는
형태"만 적는다.**

## 13. 2단계: 서버 저장

1단계 출시 후에 붙인다. 스키마와 API를 미리 정해 두는 이유는, 1단계의 세이브
구조가 나중에 서버로 옮겨질 수 있는 모양이어야 하기 때문이다.

```sql
-- V3__pet.sql
CREATE TABLE pet (
    id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    member_id BIGINT NOT NULL,
    name VARCHAR(16) NOT NULL,
    level INT NOT NULL DEFAULT 1,
    exp INT NOT NULL DEFAULT 0,
    coins INT NOT NULL DEFAULT 0,
    hunger SMALLINT NOT NULL, mood SMALLINT NOT NULL,
    clean SMALLINT NOT NULL,  energy SMALLINT NOT NULL,
    -- 인벤토리·가구 배치는 조회 조건이 될 일이 없고 모양이 자주 바뀐다.
    state_json JSON NOT NULL,
    synced_at DATETIME NOT NULL,
    CONSTRAINT uk_pet_member UNIQUE (member_id),
    CONSTRAINT fk_pet_member FOREIGN KEY (member_id) REFERENCES member (id)
);
```

**컬럼과 JSON을 섞는 이유**: 레벨·코인은 나중에 랭킹이나 통계로 조회할 값이라
컬럼으로 두고, 인벤토리처럼 조회 조건이 되지 않고 스키마가 자주 바뀌는 것은
JSON으로 둔다. 전부 JSON에 넣으면 나중에 "레벨 10 이상 사용자 수"를 못 센다.

API는 `packages/api`에 `createPetApi`로 추가한다. 경로 문자열은 거기 한 곳에만
둔다(기존 `auth.ts`와 같은 이유).

| 메서드 | 경로   | 설명                         |
| ------ | ------ | ---------------------------- |
| GET    | `/pet` | 없으면 404 (신규 사용자)     |
| PUT    | `/pet` | 스냅샷 전체 + `baseSyncedAt` |

**충돌 처리**: 서버의 `synced_at`이 클라이언트가 보낸 `baseSyncedAt`보다 최신이면
409와 함께 서버 상태를 돌려준다. 클라이언트는 **자동으로 병합하지 말고**
사용자에게 "다른 기기에 더 최근 진행이 있어요. 어느 쪽을 쓸까요?"를 묻는다.
조용한 자동 병합은 진행이 사라지는 사고의 원인이 된다.

`GameName`에 `'PET'`을 추가하는 것은 **랭킹을 붙일 때만** 한다. 그 시점에는
점수를 서버가 검증해야 하고, 그건 별도 설계다.

## 16. 열린 질문

구현 시작 전에 답이 필요한 순서대로.

1. **앱 이름.** 이 문서는 "펫타운"으로 썼다.
2. **펫 이름의 기본값.** 튜토리얼 1단계에서 사용자가 짓지만, 입력 없이 넘어갈
   때 쓸 기본 이름이 필요하다.
3. **사운드.** 넣는다면 M5. 도트 게임은 무음이면 심심하지만, 모바일 웹에서는
   자동 재생 정책 때문에 첫 탭 이후에만 소리를 켤 수 있다.
